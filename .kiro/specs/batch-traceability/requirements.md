# Requirements Document

## Introduction

本特性将走步机（产品成品）的溯源粒度从「单台 / 单部件」调整为「按生产批次」。核心变化：

- 二维码从「每台一个主码 + 若干部件码」改为「每个生产批次一个二维码」。
- 扫描该批次二维码即可一次性登记该批次的全部台数（例如一批 1000 台，扫一次登记 1000 台）。
- 溯源以「生成批次 + 生成时间」为主参考，不再依赖逐台、逐部件的装配扫码与逐台族谱。

这是对现有系统既有行为的**替换**（现系统为 Flask + SQLite，`user_version = 11`，采用增量非破坏性迁移）。本特性必须明确既有数据（已生成的单台二维码、`machines`、`trace_records` 等）的兼容与迁移预期，并保留产品、供应商、账号等无关功能不变。侧边栏样式改造为独立的已完成特性，不在本特性范围内。

> 说明：文档末尾「已确认决策」小节记录了关键设计决策（A–G 为批次溯源，H–L 为领星集成，M–R 为角色模型与新增能力），均已与用户确认。

> 新增范围：本次在保留全部既有需求（Requirement 1–11）的前提下，追加**领星（Lingxing）ERP 系统集成**（Requirement 12–20）——本系统为数据源头，向领星单向推送采购订单与入库数据；并进一步补充**三角色权限模型**（管理员 / 仓管 / 运营）、**系统设置页面**、**用户管理**、**生产订单（由采购订单生成并自动绑定唯一生产二维码）**、**扫码枪入库**、**采购单导出格式**、**库存同步至领星**与**工厂进度可见性**（Requirement 21–27）。

> 角色模型（已确认）：系统仅有三个角色——**管理员（ADMIN）**、**仓管（WAREHOUSE）**、**运营（OPERATIONS）**；单个用户账号恰好持有其中一个角色。既有「录入员」角色已被撤销，其现场扫码登记 / 入库能力并入仓管。管理员拥有全部权限，并独占系统设置与用户管理；仓管兼具原录入员能力，负责由运营提交的采购订单生成生产订单（自动绑定唯一生产二维码、与生产批次机制同步）、扫码枪入库、以及生产完成后的库存同步；运营负责创建采购订单、查看工厂进度、执行领星入库与库存同步至领星。

## Glossary

- **走步机（Treadmill / Product_Unit）**：本系统追溯的成品单位；单台不再单独生成二维码。
- **生产批次（Production_Batch）**：一次生产任务，包含产品型号、计划台数、生成时间、前缀与操作人。
- **批次二维码（Batch_QR）**：代表一个生产批次的唯一二维码；一个批次仅一个二维码。
- **批次码值（Batch_Code）**：批次二维码所编码的全局唯一标识字符串。
- **批次二维码生成器（BatchCodeGenerator）**：接收生成请求、创建生产批次与批次二维码、并扣减库存的服务组件。
- **批次登记记录（Batch_Trace_Record）**：一次扫码登记形成的批次级溯源记录，携带登记台数、操作人、时间与质量状态。
- **批次录入服务（BatchEntryService）**：处理扫描批次二维码并生成批次登记记录的服务组件。
- **批次溯源查询服务（BatchTraceQueryService）**：处理扫描批次二维码进行只读溯源查询、返回批次参考信息与批次级反向追溯清单的服务组件，不产生任何登记或数据变更。
- **批次溯源系统（System）**：本特性涉及的整体后端系统的统称。
- **每套用量（Per_Unit_Usage）**：产品定义中每台走步机对某供应部件的消耗数量。
- **供应批次（Supplier_Inventory_Batch）**：供应部件的到货批次与结存，沿用现有 `supplier_inventory_batches`。
- **迁移程序（MigrationRunner）**：执行数据库 `user_version` 升级的增量迁移逻辑。
- **管理员（ADMIN）**：拥有全部权限的角色；独占系统设置与用户管理（含录入领星凭据），并可配置产品 / 供应商，且可生成生产批次 / 生产订单与批次二维码。
- **仓管（WAREHOUSE）**：兼具原录入员能力的角色；可对授权产品执行现场扫码登记、由运营提交的采购订单生成生产订单（自动绑定唯一生产二维码）、执行扫码枪入库，并在生产完成后同步库存。原「录入员（Operator）」角色已撤销，其能力并入仓管。
- **运营（OPERATIONS）**：负责在本系统创建采购订单、查看工厂进度、将采购订单推送至领星、执行领星入库并将最新库存同步至领星的角色。
- **质量状态（Quality_Status）**：批次登记记录的检验状态，取值为 待检（ASSEMBLED）、合格（PASSED）、暂扣（HOLD）。
- **领星（Lingxing）**：外部下游 ERP 系统；本系统为数据源头，向领星单向推送采购订单与入库数据。领星 OpenAPI 主机为 `https://openapi.lingxing.com`。
- **领星集成服务（LingxingIntegrationService）**：负责领星凭据管理、令牌获取与刷新、请求签名、推送、重试与同步状态维护的服务组件。
- **领星凭据（Lingxing_Credentials）**：调用领星 OpenAPI 所需的 appId、appSecret 与 id，作为配置 / 密钥管理，尚未提供；后续由管理员在系统设置页面录入。凭据须安全存储（不硬编码于源代码）、在日志与界面中脱敏。
- **系统设置页面（System_Settings_Page）**：仅限管理员访问的通用设置页面，承载通用系统设置与领星凭据（appId / appSecret / id）录入。
- **用户管理（User_Management）**：仅限管理员访问的用户账号管理功能（由原「录入员管理」更名而来），可新增用户并编辑其角色（仓管 / 运营 / 管理员）。
- **生产订单（Production_Order）**：由仓管针对某条运营提交的采购订单生成的生产单据；生成时自动绑定恰好一个唯一的生产二维码（与生产批次机制同步），并关联其来源采购订单。
- **生产二维码（Production_QR）**：代表一个生产订单 / 生产批次的唯一二维码；一个二维码代表整批产品（如 1000 张床架共用一个二维码）。
- **扫码枪入库（Scan_Gun_Inbound）**：仓管使用扫码枪扫描生产二维码检索对应生产订单后，在弹窗中填写入库数量完成入库，并将该数量累加至该产品的仓库库存数。
- **采购单导出（Purchase_Order_Export）**：将本系统的采购订单导出为规定列格式的电子表格，供人工导入领星。
- **库存同步（Inventory_Sync）**：由运营将本系统最新库存单向推送（PUSH）至领星的操作。
- **工厂进度（Factory_Progress）**：针对某条采购订单，是否已生成生产订单及其最新生产 / 入库数量的可见信息，供运营查看。
- **访问令牌（Access_Token）**：领星 OpenAPI 用于业务请求鉴权的 access_token，具有到期时间。
- **刷新令牌（Refresh_Token）**：用于在访问令牌过期时换取新访问令牌的 refresh_token。
- **请求签名（Request_Signature / sign）**：向领星业务接口发送请求时，依据请求参数、访问令牌与时间戳（timestamp）计算得到的签名参数。
- **采购订单（Purchase_Order）**：由运营在本系统创建、并推送至领星的采购单据。
- **入库收货记录（Inbound_Receipt）**：由仓管针对采购订单执行入库（收货）后在本系统生成的收货记录。
- **领星入库（Lingxing_Inbound_Push）**：由运营执行、将入库收货记录推送至领星的操作。
- **同步状态（Sync_Status）**：采购订单或入库收货记录相对领星的推送状态，取值为 待推送（PENDING）、已推送（PUSHED）、推送失败（FAILED）。

## Requirements

### Requirement 1: 按批次生成单一二维码

**User Story:** 作为管理员或仓管，我想为一个生产批次生成一个二维码，以便用一个码代表整批走步机，而不必为每台生成主码与部件码。

#### Acceptance Criteria

1. WHEN 管理员或仓管提交同时包含产品型号、计划台数与前缀且三者均非空的批次生成请求, THE BatchCodeGenerator SHALL 在同一次操作中创建恰好一个生产批次并生成恰好一个批次二维码。
2. THE BatchCodeGenerator SHALL 为每个生产批次分配一个在全系统范围内唯一的批次码值。
3. WHEN 管理员输入的计划台数为 1 至 999,999（含）之间的整数, THE BatchCodeGenerator SHALL 将该数值记录为该生产批次的台数。
4. IF 计划台数为空、非整数、小于 1 或大于 999,999, THEN THE BatchCodeGenerator SHALL 拒绝该请求、不创建生产批次、不生成批次二维码、不扣减任何供应库存，并返回指明台数取值范围的描述性错误信息。
5. WHEN 生产批次创建成功, THE BatchCodeGenerator SHALL 记录该批次的生成时间、前缀、产品型号、计划台数与操作人。
6. WHEN 管理员或仓管对一个已存在的生产批次请求下载其批次二维码, THE BatchCodeGenerator SHALL 提供该生产批次的批次二维码文件。
7. IF 批次生成请求缺少产品型号或前缀, THEN THE BatchCodeGenerator SHALL 拒绝该请求、不创建生产批次、不生成批次二维码，并返回指明缺失字段的描述性错误信息。
8. IF 请求下载的生产批次不存在, THEN THE BatchCodeGenerator SHALL 拒绝该请求并返回描述性错误信息。
9. IF 新生成的批次码值与既有批次码值重复, THEN THE BatchCodeGenerator SHALL 不创建该生产批次、不生成批次二维码，并返回描述性错误信息。

### Requirement 2: 扫码一次性登记整批台数

**User Story:** 作为仓管，我想扫描批次二维码就一次性登记整批走步机，以便省去逐台、逐部件扫码。

#### Acceptance Criteria

1. WHEN 仓管扫描一个批次二维码，且该二维码对应的生产批次存在、属于已授权给该仓管的产品、且尚无批次登记记录, THE BatchEntryService SHALL 创建一条批次登记记录，其登记台数等于该生产批次的台数。
2. WHEN 创建批次登记记录, THE BatchEntryService SHALL 在该单条记录中记录操作人、登记时间与所属生产批次，且不创建任何逐台记录。
3. IF 被扫描的批次二维码不存在，或其对应产品未授权给当前仓管, THEN THE BatchEntryService SHALL 拒绝登记、不创建任何批次登记记录，并返回指明二维码无效或未授权的描述性错误信息。
4. IF 被扫描的批次二维码对应的生产批次已存在批次登记记录, THEN THE BatchEntryService SHALL 拒绝重复登记、保持既有记录不变，并返回提示该批次已登记的描述性错误信息。
5. WHERE 仓管对本次扫描修正登记台数, THE BatchEntryService SHALL 仅接受介于 1 至该生产批次台数（含）之间的整数台数。
6. IF 修正后的登记台数非整数、小于 1 或大于该生产批次台数, THEN THE BatchEntryService SHALL 拒绝该修正、不创建或更新批次登记记录，并返回指明台数取值范围的描述性错误信息。

### Requirement 3: 批次二维码与批次记录的参考信息

**User Story:** 作为管理员，我想让批次二维码与批次记录携带批次与时间等参考信息，以便以「批次 + 时间」为依据做溯源。

#### Acceptance Criteria

1. THE BatchCodeGenerator SHALL 使批次二维码的编码信息包含该生产批次的批次码值。
2. WHEN 管理员或仓管查看某条批次登记记录, THE System SHALL 显示该记录的批次码值、产品型号、登记台数、生成时间、前缀与操作人。
3. THE System SHALL 以生成批次与生成时间作为批次登记记录溯源查询的匹配依据。
4. WHEN 管理员按生成批次或按时间范围（起始时间至结束时间，含起止边界）查询, THE System SHALL 返回全部匹配的批次登记记录列表，并按生成时间由近及远排序。
5. IF 查询条件未匹配到任何批次登记记录, THEN THE System SHALL 返回空列表且不返回错误。
6. IF 时间范围查询的起始时间晚于结束时间, THEN THE System SHALL 拒绝该查询并返回描述性错误信息。

### Requirement 4: 库存扣减仍按整批用量

**User Story:** 作为管理员，我想在生成批次时按整批消耗扣减供应库存，以便库存结存与实际生产一致。

#### Acceptance Criteria

1. WHEN 生成一个计划台数为 N（N 为正整数）的生产批次, THE BatchCodeGenerator SHALL 对该产品定义中每套用量大于 0 的每种供应部件，按「N × 每套用量」计算所需扣减数量，从其对应供应批次的可用结存中扣减该数量，并为每次扣减生成一条领用（ISSUE）流水。
2. IF 任一供应部件的所需扣减数量大于其对应供应批次当前可用结存之和, THEN THE BatchCodeGenerator SHALL 判定为结存不足，使整次生成失败，不扣减任何供应批次、不生成领用流水、不创建生产批次、不生成批次二维码，并返回指明哪种供应部件结存不足的描述性错误信息。
3. THE BatchCodeGenerator SHALL 在同一个数据库事务内完成库存扣减、领用流水写入、生产批次创建与批次二维码生成。
4. IF 该事务中任一步骤失败, THEN THE BatchCodeGenerator SHALL 回滚整个事务，使数据库恢复至生成前的一致状态，且不遗留任何部分扣减、领用流水或二维码。
5. WHILE 存在多个并发的批次生成请求消耗同一供应批次, THE BatchCodeGenerator SHALL 串行化对该供应批次可用结存的扣减，确保各请求的累计扣减不超过该供应批次的可用结存。

### Requirement 5: 批次级供应批次关联与反向追溯

**User Story:** 作为管理员，我想知道某生产批次消耗了哪些供应批次，以便在批次粒度上做反向追溯与召回范围判断。

#### Acceptance Criteria

1. WHEN 生成一个生产批次成功, THE BatchCodeGenerator SHALL 在与库存扣减、批次创建相同的数据库事务内，为每个被消耗的供应批次创建一条批次级关联记录，包含供应批次标识、对应供应部件与该供应批次的消耗数量。
2. THE BatchCodeGenerator SHALL 使某生产批次针对同一供应部件的各关联记录消耗数量之和，等于该批次「计划台数 × 该供应部件的每套用量」。
3. WHEN 管理员查看某已存在生产批次的反向追溯, THE System SHALL 返回该批次关联的每条供应批次记录，每条包含供应批次标识、供应部件与消耗数量。
4. IF 用于反向追溯查询的生产批次不存在, THEN THE System SHALL 拒绝该查询并返回描述性错误信息。
5. WHEN 管理员按某已存在供应批次查看正向追溯, THE System SHALL 返回消耗该供应批次的每个生产批次，每条包含批次码值、产品型号、生成时间与该供应批次的消耗数量。
6. WHERE 没有任何生产批次消耗被查询的供应批次, THE System SHALL 返回空清单而非错误信息。

### Requirement 6: 批次级质量状态闭环

**User Story:** 作为管理员，我想在批次级别管理质量状态，以便对整批走步机做放行或暂扣。

#### Acceptance Criteria

1. WHEN 批次登记记录创建成功, THE System SHALL 将其质量状态初始化为待检（ASSEMBLED）。
2. WHILE 批次登记记录处于待检（ASSEMBLED）状态, WHEN 管理员对其执行合格确认, THE System SHALL 将质量状态更新为合格（PASSED）。
3. WHILE 批次登记记录处于待检（ASSEMBLED）状态, WHEN 管理员对其执行暂扣并填写长度为 1 至 500 个字符的原因, THE System SHALL 将质量状态更新为暂扣（HOLD）并保存该原因。
4. IF 管理员执行暂扣但原因为空或超过 500 个字符, THEN THE System SHALL 拒绝该操作、保持质量状态不变，并返回指明原因长度要求的描述性错误信息。
5. IF 管理员对非待检（ASSEMBLED）状态的批次登记记录执行合格确认或暂扣, THEN THE System SHALL 拒绝该转换并保持质量状态不变。
6. WHEN 质量状态发生变化, THE System SHALL 写入一条审计事件，记录操作人、变更时间、变更前状态、变更后状态，且当变更为暂扣（HOLD）时记录暂扣原因。

### Requirement 7: 停用旧的单台 / 单部件溯源流程

**User Story:** 作为管理员，我想停用逐台、逐部件的溯源流程，以便现场只保留批次扫码这一种走步机溯源方式。

#### Acceptance Criteria

1. THE System SHALL 使走步机产品的「每台一个主码 + 逐部件扫码装配」录入入口不出现于现场录入界面。
2. WHEN 仓管选择走步机产品进行现场登记, THE System SHALL 仅提供批次扫码登记方式，且不提供每台主码或逐部件扫码装配选项。
3. IF 收到对已停用的逐台 / 逐部件装配录入入口的直接调用, THEN THE System SHALL 拒绝该请求、不创建任何逐台溯源记录，并返回指明该入口已停用的描述性错误信息。
4. WHERE 存在走步机产品的历史逐台 / 逐部件溯源数据, THE System SHALL 以只读方式保留该数据并可供查询。
5. THE System SHALL 保持产品、供应商、账号管理等无关功能可访问，且其增删改查行为与本特性实施前一致。

### Requirement 8: 既有数据兼容与迁移

**User Story:** 作为系统维护者，我想在升级时保留既有数据，以便历史二维码与溯源记录不丢失。

#### Acceptance Criteria

1. WHEN 系统启动且检测到数据库 `user_version` 低于本特性目标版本, THE MigrationRunner SHALL 以增量方式仅新增列、表与索引，且不删除、不重写既有历史数据，并保持既有各表的记录行数不减少。
2. WHEN 迁移成功完成, THE MigrationRunner SHALL 将数据库 `user_version` 从 11 更新为本特性定义的固定目标版本（一个大于 11 的确定值）。
3. WHERE 存在既有的单台二维码与逐台溯源记录, THE System SHALL 在迁移后保持这些记录的行数与既有字段值不变，并可供查询检索。
4. IF 迁移过程中任一步骤发生错误, THEN THE MigrationRunner SHALL 在同一数据库事务内回滚本次迁移的全部结构与数据变更，使数据库 `user_version`、表结构与数据均保持迁移前状态，并返回指示迁移失败的描述性错误信息。
5. IF 系统启动时检测到数据库 `user_version` 已等于或高于本特性目标版本, THEN THE MigrationRunner SHALL 跳过迁移且不对数据库结构或数据做任何更改。
6. IF 迁移失败, THEN THE System SHALL 中止启动流程且不进入对外提供服务的状态。

### Requirement 9: 角色权限约束

**User Story:** 作为系统所有者，我想在「管理员 / 仓管 / 运营」三角色模型下维护清晰的权限边界，以便批次溯源不破坏授权模型；其中仓管兼具原录入员的现场执行能力。

#### Acceptance Criteria

1. THE System SHALL 仅允许身份为管理员或仓管的用户生成生产批次与批次二维码。
2. WHERE 走步机产品已由管理员授权给某仓管, THE System SHALL 允许该仓管对该产品执行批次扫码登记。
3. IF 既非管理员亦非仓管的用户尝试生成生产批次或批次二维码, THEN THE System SHALL 拒绝该操作、不创建任何生产批次或批次二维码、不产生任何库存扣减，并返回指示权限不足的错误信息。
4. IF 仓管尝试对未授权给其的走步机产品执行批次扫码登记, THEN THE System SHALL 拒绝该登记、不创建任何批次登记记录，并返回指示权限不足的错误信息。
5. IF 未经身份认证的请求尝试生成批次二维码或执行批次扫码登记, THEN THE System SHALL 拒绝该操作、不产生任何数据变更，并返回指示需要先完成身份认证的错误信息。
6. THE System SHALL 使每个用户账号恰好持有管理员（ADMIN）、仓管（WAREHOUSE）、运营（OPERATIONS）三个角色中的一个。

### Requirement 10: 扫码查询溯源

**User Story:** 作为已授权用户，我想扫描批次二维码就查询该批次的溯源信息，以便在不做登记的前提下快速了解整批走步机的来源与状态。

#### Acceptance Criteria

1. WHEN 已完成身份认证的用户扫描一个批次二维码，且该二维码对应的生产批次存在, THE BatchTraceQueryService SHALL 返回该生产批次的只读溯源信息，包含批次码值、产品型号、计划台数、登记台数、生成时间、前缀与质量状态。
2. WHEN BatchTraceQueryService 返回某生产批次的溯源信息, THE BatchTraceQueryService SHALL 一并返回该生产批次消耗的供应批次清单（批次级反向追溯），每条包含供应批次标识、供应部件与消耗数量。
3. WHEN BatchTraceQueryService 执行扫码溯源查询, THE BatchTraceQueryService SHALL 不创建、不修改、不删除任何生产批次、批次登记记录或供应库存数据。
4. WHERE 执行扫码溯源查询的用户为管理员, THE BatchTraceQueryService SHALL 允许查询任意存在的生产批次的溯源信息。
5. WHERE 执行扫码溯源查询的用户为仓管，且被查询批次对应的产品已授权给该仓管, THE BatchTraceQueryService SHALL 返回该生产批次的只读溯源信息。
6. IF 仓管扫码查询的生产批次对应产品未授权给该仓管, THEN THE BatchTraceQueryService SHALL 拒绝该查询、不返回任何溯源信息，并返回指示权限不足的描述性错误信息。
7. IF 扫描的批次二维码不存在、批次码值无法解析或其对应的生产批次不存在, THEN THE BatchTraceQueryService SHALL 拒绝该查询、不返回溯源信息，并返回指明批次码无效或不存在的描述性错误信息。
8. IF 未经身份认证的请求尝试执行扫码溯源查询, THEN THE BatchTraceQueryService SHALL 拒绝该查询、不返回任何溯源信息，并返回指示需要先完成身份认证的描述性错误信息。

### Requirement 11: 同批次同码

**User Story:** 作为管理员，我想让同一生产批次的每台走步机都张贴同一个批次码，以便整批走步机用一个码统一标识与溯源，而不为单台生成独立码值。

#### Acceptance Criteria

1. THE BatchCodeGenerator SHALL 使一个生产批次仅对应一个批次码值，且该批次码值代表该生产批次的全部走步机。
2. THE System SHALL 使同一生产批次内生产的每台走步机均张贴该生产批次的同一批次码值标签，且不为单台走步机分配独立码值。
3. WHEN 管理员为同一已存在生产批次重复或后续打印批次二维码标签, THE System SHALL 复用该生产批次既有的批次码值，且不生成新的批次码值或逐台码值。
4. IF 收到为一个已存在批次码值的生产批次再生成一个不同批次码值的请求, THEN THE BatchCodeGenerator SHALL 拒绝该请求、不生成新的批次码值，并返回指明该生产批次已存在批次码的描述性错误信息。

### Requirement 12: 三角色权限模型（管理员 / 仓管 / 运营）

**User Story:** 作为系统所有者，我想将系统角色收敛为管理员、仓管、运营三种，以便按「配置与管理、现场执行与入库、采购与领星推送」等职责清晰分配权限。

#### Acceptance Criteria

1. THE System SHALL 恰好支持管理员（ADMIN）、仓管（WAREHOUSE）、运营（OPERATIONS）三个角色，且使每个用户账号恰好持有其中一个角色。
2. THE System SHALL 授予管理员全部权限，并使系统设置与用户管理仅限管理员执行。
3. WHEN 身份为运营的已认证用户请求创建采购订单、查看工厂进度、将采购订单推送至领星、执行领星入库或将库存同步至领星, THE System SHALL 允许该操作执行。
4. WHEN 身份为仓管的已认证用户请求由采购订单生成生产订单、执行批次扫码登记、执行扫码枪入库或在生产完成后同步库存, THE System SHALL 允许该操作执行。
5. IF 未经身份认证的请求尝试执行创建采购订单、生成生产订单、推送采购订单、扫码枪入库、领星入库或库存同步等操作, THEN THE System SHALL 拒绝该请求、不产生任何数据变更，并返回指示需要先完成身份认证的描述性错误信息。
6. IF 已认证但角色不匹配的用户尝试执行仅限管理员、仅限运营或仅限仓管的操作, THEN THE System SHALL 拒绝该操作、不产生任何数据变更，并返回指示权限不足的描述性错误信息。

### Requirement 13: 领星凭据安全配置与缺失降级

**User Story:** 作为系统维护者，我想以安全配置方式管理领星 appId、appSecret 与 id，以便在不硬编码密钥的前提下先构建功能、由管理员后续在系统设置中录入凭据，并在凭据缺失时安全降级。

#### Acceptance Criteria

1. THE LingxingIntegrationService SHALL 仅从运行时配置或密钥来源（如管理员在系统设置页面录入并安全存储的凭据、环境变量或配置文件）读取领星凭据（appId、appSecret 与 id），且不在源代码或版本库文件中内置 appId、appSecret 或 id 的明文值。
2. IF 领星凭据（appId、appSecret 或 id）缺失、为空字符串或仅包含空白字符, WHEN 任一需要调用领星接口的操作被触发, THEN THE LingxingIntegrationService SHALL 拒绝该次外部调用、不向领星主机发起任何网络请求、不修改任何本地业务数据，并返回指明领星凭据未配置的描述性错误信息。
3. WHERE 领星凭据已配置（appId、appSecret 与 id 均非空且不仅含空白字符）, THE LingxingIntegrationService SHALL 使用配置中的 appId、appSecret 与 id 向领星 OpenAPI 主机 `https://openapi.lingxing.com` 发起认证与业务请求。
4. THE LingxingIntegrationService SHALL 在日志与接口响应中对 appSecret、id、access_token 与 refresh_token 进行脱敏，即不输出其完整明文、至多保留末尾 4 位字符、其余字符一律以掩码字符替换。
5. WHILE 领星凭据缺失、为空字符串或仅包含空白字符, THE LingxingIntegrationService SHALL 保持系统中不依赖领星集成的其余功能正常运行，且不因领星凭据缺失而中断服务启动或使系统进入整体不可用状态。

### Requirement 14: 访问令牌获取、缓存与自动刷新

**User Story:** 作为集成开发者，我想自动获取并维护领星访问令牌，以便业务请求始终携带有效令牌而无需人工干预。

#### Acceptance Criteria

1. WHEN 需要调用领星业务接口且本地缓存中不存在有效访问令牌（缓存为空，或当前时间已达到“访问令牌到期时间减去 60 秒安全余量”）, THE LingxingIntegrationService SHALL 使用 appId 与 appSecret 向领星换取访问令牌（access_token）与刷新令牌（refresh_token），且单次令牌请求的等待超时为 10 秒。
2. WHEN 成功获取访问令牌, THE LingxingIntegrationService SHALL 缓存该访问令牌、对应的刷新令牌及访问令牌到期时间，并在“当前时间早于访问令牌到期时间减去 60 秒安全余量”期间，对后续业务请求复用该缓存的访问令牌。
3. WHEN 需要调用领星业务接口且缓存的访问令牌已过期（当前时间已达到“访问令牌到期时间减去 60 秒安全余量”）而刷新令牌仍有效, THE LingxingIntegrationService SHALL 使用刷新令牌换取新的访问令牌，并更新缓存中的访问令牌及到期时间。
4. IF 刷新令牌无效或刷新令牌请求失败, THEN THE LingxingIntegrationService SHALL 使用 appId 与 appSecret 重新获取访问令牌与刷新令牌，并更新缓存中的访问令牌、刷新令牌及到期时间。
5. IF 单次令牌获取或刷新请求因网络错误或超时而失败, THEN THE LingxingIntegrationService SHALL 对该请求最多重试 2 次（累计请求不超过 3 次），且相邻两次请求的间隔不少于 1 秒。
6. IF 访问令牌的获取与刷新在重试次数耗尽后均失败, THEN THE LingxingIntegrationService SHALL 中止本次领星调用、不修改任何本地业务数据（保持调用前的数据状态），并返回指明令牌获取失败原因的描述性错误信息。

### Requirement 15: 领星请求签名

**User Story:** 作为集成开发者，我想按领星规范对业务请求签名，以便请求通过领星鉴权。

#### Acceptance Criteria

1. WHEN 向领星发起业务请求, THE LingxingIntegrationService SHALL 依据该请求的请求参数、当前有效访问令牌与请求发起时刻的时间戳（timestamp，采用领星官方文档规定的时间单位与格式）计算签名参数（sign）。
2. WHEN 已成功计算出签名参数, THE LingxingIntegrationService SHALL 将 sign 与用于该次计算的同一 timestamp 随该请求一并发送，且不修改请求中参与签名计算的任何参数值。
3. IF 缺少计算签名所需的有效访问令牌或任一必要请求参数, THEN THE LingxingIntegrationService SHALL 中止本次领星业务请求、不发起外部调用、不修改任何本地业务数据，并返回指明无法生成请求签名的描述性错误信息。
4. THE LingxingIntegrationService SHALL 使领星接口的具体路径、请求字段映射与签名算法细节可经运行时配置或密钥来源（如配置文件或环境变量）提供而无需修改源代码，并以领星官方文档（`https://apidoc.lingxing.com/`）为准在凭据可用后确认。

### Requirement 16: 运营下采购订单并推送至领星

**User Story:** 作为运营，我想在本系统下采购订单并将其推送到领星，以便领星侧同步该采购订单。

#### Acceptance Criteria

1. WHEN 运营提交同时包含供应商、商品与采购数量，且采购数量为 1 至 999,999（含）之间整数的采购订单创建请求, THE System SHALL 在本系统中创建一条采购订单记录，记录供应商、商品、采购数量、创建人与创建时间，并将其同步状态初始化为待推送（PENDING）。
2. IF 采购订单创建请求缺少供应商、商品或采购数量中的任一必填字段, THEN THE System SHALL 拒绝该请求、不创建采购订单、不产生任何数据变更，并返回指明缺失字段的描述性错误信息。
3. IF 采购数量为空、非整数、小于 1 或大于 999,999, THEN THE System SHALL 拒绝该请求、不创建采购订单、不产生任何数据变更，并返回指明采购数量有效取值范围为 1 至 999,999（含）整数的描述性错误信息。
4. WHEN 运营对一条本地已存在、且同步状态为待推送（PENDING）或推送失败（FAILED）的采购订单执行推送, THE LingxingIntegrationService SHALL 将该采购订单发送至领星，并在领星于 30 秒内返回成功后本地保存领星侧返回的采购订单标识与原始响应，并将该采购订单同步状态更新为已推送（PUSHED）。
5. IF 一条采购订单同步状态已为已推送（PUSHED）, WHEN 再次对其执行推送, THEN THE LingxingIntegrationService SHALL 不发起领星调用、不在领星侧重复创建采购订单、保持本地已记录的领星采购订单标识不变，并返回指明该采购订单已推送的描述性信息。
6. IF 领星接口在推送采购订单时返回失败，或推送请求在 30 秒内未收到领星响应, THEN THE LingxingIntegrationService SHALL 保持本系统采购订单记录存在、将其同步状态标记为推送失败（FAILED），并返回包含领星错误信息的描述性错误。

### Requirement 17: 仓管针对采购订单执行入库

**User Story:** 作为仓管，我想针对采购订单执行入库收货，以便记录到货并为后续领星入库做准备。

#### Acceptance Criteria

1. WHEN 已认证的仓管针对一条本地已存在的采购订单提交入库请求，且入库数量为 1 至 999,999（含）之间的整数, THE System SHALL 创建一条入库收货记录，关联该采购订单，将收货人记录为提交该请求的仓管用户、将系统当前时间记录为收货时间、记录该入库数量，将其同步状态初始化为待推送（PENDING），并向请求方返回新建入库收货记录的标识作为成功确认。
2. IF 入库请求未提供采购订单引用，或所引用的采购订单在本系统中不存在, THEN THE System SHALL 拒绝该请求、不创建入库收货记录、不产生任何数据变更，并返回指明采购订单缺失或不存在的描述性错误信息。
3. IF 入库数量为空、非整数、小于 1 或大于 999,999, THEN THE System SHALL 拒绝该请求、不创建入库收货记录、不产生任何数据变更，并返回指明入库数量有效取值范围为 1 至 999,999（含）整数的描述性错误信息。

### Requirement 18: 运营执行领星入库推送

**User Story:** 作为运营，我想执行领星入库把入库收货推送到领星，以便领星侧同步入库单。

#### Acceptance Criteria

1. WHEN 运营对一条本地已存在、且同步状态为待推送（PENDING）或推送失败（FAILED）的入库收货记录执行领星入库, THE LingxingIntegrationService SHALL 将该入库收货推送至领星，并在成功后本地保存领星侧返回的入库单标识与原始响应，并将该入库收货同步状态更新为已推送（PUSHED）。
2. IF 领星入库引用的入库收货记录不存在, THEN THE LingxingIntegrationService SHALL 拒绝该操作、不发起领星调用，并返回指明入库收货记录不存在的描述性错误信息。
3. IF 一条入库收货所属的采购订单同步状态不为已推送（PUSHED）, WHEN 运营对其执行领星入库, THEN THE LingxingIntegrationService SHALL 拒绝该领星入库、不发起入库推送、保持该入库收货同步状态不变，并返回指明需先成功推送采购订单的描述性错误信息。
4. IF 一条入库收货同步状态已为已推送（PUSHED）, WHEN 再次对其执行领星入库, THEN THE LingxingIntegrationService SHALL 不发起领星调用、不在领星侧重复创建入库单、保持本地已记录的领星入库单标识与同步状态不变，并返回本地已记录的领星入库单标识。
5. IF 领星接口在推送入库单时返回失败，或推送请求在 30 秒内未收到领星响应, THEN THE LingxingIntegrationService SHALL 保持本地入库收货记录存在、保持其已记录的领星入库单标识不变、将其同步状态标记为推送失败（FAILED），并返回包含领星错误信息的描述性错误。
6. WHILE 一条入库收货的领星入库推送正在进行, IF 再次对同一入库收货执行领星入库, THEN THE LingxingIntegrationService SHALL 拒绝该重复请求、不发起新的领星调用、保持该入库收货同步状态不变，并返回指明该入库收货推送正在进行中的描述性错误信息。

### Requirement 19: 领星推送的重试与错误处理

**User Story:** 作为集成开发者，我想对领星接口失败进行有界重试与清晰错误处理，以便应对瞬时故障且不产生重复副作用。

#### Acceptance Criteria

1. THE LingxingIntegrationService SHALL 提供可配置的最大重试次数（0 至 10 次之间的整数，默认 3 次）、可配置的单次请求超时（1 至 120 秒之间，默认 30 秒）与可配置的重试间隔（1 至 60 秒之间，默认 2 秒）。
2. WHEN 对领星的推送请求因可重试错误（网络超时、连接失败、领星返回的限流或临时性服务端错误）失败, THE LingxingIntegrationService SHALL 在不超过配置的最大重试次数范围内，按配置的重试间隔进行有界重试，且每次请求以配置的单次请求超时为上限。
3. IF 领星推送请求因不可重试错误（鉴权失败、凭据无效或参数校验失败）而失败, THEN THE LingxingIntegrationService SHALL 不进行重试、保持对应记录本地存在且不产生部分修改、将其同步状态标记为推送失败（FAILED），并返回包含领星错误信息的描述性错误。
4. IF 达到配置的最大重试次数后仍失败, THEN THE LingxingIntegrationService SHALL 停止重试、保持对应记录本地存在且不产生部分修改、将其同步状态标记为推送失败（FAILED），并返回包含领星错误信息的描述性错误。
5. WHILE 对同一业务对象执行重试, THE LingxingIntegrationService SHALL 保持推送的幂等性，使无论重试多少次都不在领星侧产生重复的采购订单或入库单。

### Requirement 20: 同步状态、领星标识记录与审计日志

**User Story:** 作为运营，我想在本系统看到每次推送的领星标识与同步状态并留有审计记录，以便核对与排查。

#### Acceptance Criteria

1. THE System SHALL 为每条采购订单与每条入库收货记录维护恰好一个当前同步状态，其取值仅限于待推送（PENDING）、已推送（PUSHED）、推送失败（FAILED）三者之一，并在记录创建时初始化为待推送（PENDING）。
2. WHEN 一次领星推送（采购订单推送或领星入库）成功, THE System SHALL 本地保存领星侧返回的对象标识与原始响应、记录本次推送完成时间，并将对应记录的同步状态更新为已推送（PUSHED）。
3. WHEN 任一领星推送操作（采购订单推送或领星入库）被执行, THE System SHALL 写入一条审计事件，记录操作人、操作类型、目标对象标识、操作时间与推送结果，且当推送失败时一并记录领星返回的错误信息。
4. WHEN 已认证的运营查询某一本地已存在的采购订单或入库收货记录的推送情况, THE System SHALL 返回其当前同步状态、已记录的领星标识与最近一次推送时间，且当该记录从未成功推送时，领星标识与最近一次推送时间返回为空。
5. IF 查询的采购订单或入库收货记录在本系统中不存在, THEN THE System SHALL 拒绝该查询、不返回推送情况，并返回指明该记录不存在的描述性错误信息。
6. THE System SHALL 持久化保存所有领星推送审计事件，且不允许对已写入的审计事件进行修改或删除。

### Requirement 21: 系统设置页面

2. THE System SHALL 使一个生产订单恰好对应一个生产二维码，为每个生产二维码分配一个在全系统范围内唯一的生产二维码码值，且该二维码代表该生产订单对应批次的全部产品。

### Requirement 24: 扫码枪入库

**User Story:** 作为仓管，我想在工厂生产完成后用扫码枪扫描生产二维码来入库，以便把入库数量累加到该产品的仓库库存。

#### Acceptance Criteria

1. WHEN 仓管使用扫码枪扫描一个生产二维码, THE System SHALL 依据该二维码检索其对应的生产订单，返回该生产订单及其关联产品的标识信息，并弹出用于填写入库数量的弹窗。
2. WHERE 仓管在某条入库数据行上点击其入库按钮, THE System SHALL 弹出用于填写该行入库数量的弹窗，并在弹窗中预置该行对应的生产订单及产品标识信息。

5. IF 扫描的生产二维码无法检索到对应生产订单, THEN THE System SHALL 拒绝该入库、不产生任何入库记录、不修改任何库存数据，并返回指明生产二维码无效或对应生产订单不存在的描述性错误信息。
6. IF 提交的入库数量为空、非整数、小于 1 或大于 999,999, THEN THE System SHALL 拒绝该入库、不产生任何入库记录、不修改任何库存数据，并返回指明入库数量有效取值范围为 1 至 999,999（含）整数的描述性错误信息。
7. IF 既非仓管亦非管理员的用户或未经身份认证的请求尝试执行扫码枪入库, THEN THE System SHALL 拒绝该入库、不产生任何入库记录、不修改任何库存数据，并返回指示权限不足或需要先完成身份认证的描述性错误信息。

### Requirement 26: 库存同步至领星

**User Story:** 作为运营，我想把最新库存单向推送到领星，以便领星侧库存与本系统保持一致。

#### Acceptance Criteria

1. WHEN 运营触发库存同步, THE LingxingIntegrationService SHALL 将本系统中各产品的当前仓库库存数量单向推送（PUSH）至领星，并在领星于 30 秒内返回成功后本地保存领星侧返回的对象标识与原始响应、记录本次同步时间，并将本次同步状态更新为已推送（PUSHED）。
2. THE System SHALL 支持运营以手动方式或经领星 API 方式执行库存同步，且仅向领星推送、不从领星拉取库存。
3. WHEN 一次库存同步被执行, THE System SHALL 写入一条审计事件，记录操作人、操作类型、同步时间与同步结果，且当同步失败时一并记录领星返回的错误信息。
4. IF 领星凭据未配置, WHEN 运营触发库存同步, THEN THE LingxingIntegrationService SHALL 拒绝该次外部调用、不向领星发起任何网络请求、不修改任何本地业务数据，并返回指明领星凭据未配置的描述性错误信息。
5. IF 领星接口在库存同步时返回失败，或推送请求在 30 秒内未收到领星响应, THEN THE LingxingIntegrationService SHALL 保持本系统库存数据不变、将本次同步状态标记为推送失败（FAILED），并返回包含领星错误信息的描述性错误。
6. WHILE 一次库存同步的领星推送正在进行, IF 再次触发库存同步, THEN THE LingxingIntegrationService SHALL 拒绝该重复请求、不发起新的领星调用、保持本次同步状态不变，并返回指明库存同步正在进行中的描述性错误信息。
7. IF 既非运营亦非管理员的用户或未经身份认证的请求尝试执行库存同步, THEN THE System SHALL 拒绝该操作、不产生任何数据变更，并返回指示权限不足或需要先完成身份认证的描述性错误信息。

### Requirement 27: 工厂进度可见性

2. WHERE 某采购订单尚未生成生产订单, THE System SHALL 将其「已生成生产订单」输出为否，且将其最新生产 / 入库数量输出为 0。
3. IF 运营查看工厂进度所引用的采购订单在本系统中不存在, THEN THE System SHALL 拒绝该查询、不返回工厂进度信息，并返回指明采购订单不存在的描述性错误信息。
4. IF 既非运营亦非管理员的用户或未经身份认证的请求尝试查看工厂进度, THEN THE System SHALL 拒绝该查询、不返回任何工厂进度信息，并返回指示权限不足或需要先完成身份认证的描述性错误信息。

## 已确认决策（A–G）

以下关键决策均已与用户确认：

- **A（登记形态）**：扫码登记形成「单条携带数量（如 1000）的批次记录」，而非 1000 条单台记录。
- **B（旧流程处置）**：走步机的逐部件扫码与逐台族谱停用，由新批次流程取代；历史记录只读保留。
- **C（历史数据）**：采用非破坏性增量迁移，历史单台二维码与溯源记录只读保留。
- **D（供应批次关联）**：在批次粒度保留「生产批次 ↔ 供应批次」关联以支持反向追溯；不再保留逐部件绑定。
- **E（库存扣减）**：生成批次仍按「N × 每套用量」扣减供应库存。
- **F（二维码/记录信息）**：批次二维码/记录携带批次码值、产品型号、登记台数、生成时间、前缀、操作人。
- **G（质量状态）**：待检/合格/暂扣状态闭环在批次级沿用。

## 已确认决策（H–L：领星集成）

以下领星（Lingxing）集成决策均已与用户确认：

- **H（数据流向）**：本系统为数据源头，向领星**单向推送**（PUSH）；领星为下游接收方。非拉取、非双向。
- **I（业务流程）**：运营在本系统「下采购订单」→ 采购订单推送至领星；仓管针对采购订单「入库」；运营执行「领星入库」将入库收货推送至领星。
- **J（角色）**：已收敛为三角色模型（管理员 / 仓管 / 运营），详见「已确认决策（M–R）」M 项；原「新增运营 + 仓管两独立角色、映射 ADMIN/OPERATOR 为备选」的表述作废。下采购订单 / 推送 / 领星入库 / 库存同步限运营，生成生产订单 / 扫码枪入库限仓管。
- **K（凭据）**：appId / appSecret / id 尚未提供，功能先行构建，后续由管理员在系统设置页面录入；以配置 / 密钥管理，不硬编码，日志与界面脱敏；凭据缺失时清晰报错并安全降级。
- **L（OpenAPI 事实）**：主机 `https://openapi.lingxing.com`；OAuth 式换取 access_token（appId + appSecret）、refresh_token 刷新、请求以 sign（参数 + access_token + timestamp）签名；具体端点路径与字段映射以领星官方文档（`https://apidoc.lingxing.com/`）为准，凭据可用后确认，作为可配置项。

## 已确认决策（M–R：角色模型与新增能力）

以下决策均已与用户确认：

- **M（三角色模型）**：系统仅有三个角色——管理员（ADMIN）、仓管（WAREHOUSE）、运营（OPERATIONS），单账号恰好持有一个角色。原「录入员」角色撤销，其现场扫码登记 / 入库能力并入仓管。管理员拥有全部权限并独占系统设置与用户管理；仓管负责由采购订单生成生产订单、扫码枪入库、批次扫码登记与生产完成后库存同步；运营负责创建采购订单、查看工厂进度、领星入库与库存同步至领星。生成生产批次 / 生产订单的授权由「仅管理员」放宽为「管理员与仓管」。
- **N（生产订单与唯一生产二维码）**：仓管通过弹窗选择运营提交的采购订单生成生产订单，生成时与生产批次机制同步并自动绑定恰好一个唯一生产二维码；一个二维码代表整批产品（如 1000 张床架共用一个二维码）；生产订单关联其来源采购订单，并支持「单产品单行」数据展示。
- **O（扫码枪入库累加库存）**：仓管以扫码枪扫描生产二维码检索对应生产订单，经弹窗填写入库数量；亦可在单条入库数据行上点击按钮打开弹窗填写；入库数量累加到对应产品的仓库库存数（如扫码登记后库存显示 1000）。
- **P（采购单导出格式）**：本系统可将采购订单导出为规定列格式的电子表格供人工导入领星；导出须包含约定的全部列，其中带星号的为必填列须填充；单元格布局作为可配置项，以样例文件为准确认。
- **Q（凭据后录）**：领星 appId / appSecret / id 暂不可用，功能先行构建，后续由管理员在系统设置页面录入；凭据须安全存储（不硬编码于源代码）、日志与界面脱敏，未配置时清晰报错并优雅降级。
- **R（数据流向再确认，含库存同步）**：本系统为数据源头，向领星**单向推送**（PUSH-only）。采购订单由运营在本系统录入，随后既可经 API 自动同步至领星，也可从本系统导出为规定格式电子表格供人工导入领星；最新库存亦由运营（手动或经 API）单向同步至领星。系统不从领星导入 / 拉取采购订单。
