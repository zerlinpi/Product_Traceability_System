# 聚星同创仓库管理系统

这是一个完全独立的局域网仓库管理系统。程序、SQLite 数据库、导出文件和独立 Python 环境全部位于 `Product_Traceability_System` 目录内，不依赖也不修改 App、App 后端、管理后台或固件工程。

## 快速开始（部署与各角色上手）

### 一、部署与初始化（管理员一次性完成）

1. **安装环境**：在服务器电脑双击 `install.bat`，脚本会在本目录创建独立 `.venv`，不污染其他项目。
2. **启动服务**：双击 `start.bat`，浏览器打开 `http://127.0.0.1:5080`。局域网其他工位访问 `http://<服务器电脑IP>:5080`（需放行 Windows 防火墙 TCP 5080 入站，且处于同一局域网）。
3. **首次登录**：使用引导管理员 `admin` / `Admin@12345` 登录，系统会强制修改密码后才能进入。
4. **创建人员账号**：进入“用户管理”，按实际人员创建仓管（WAREHOUSE）和运营（OPERATIONS）账号。仓管无需再挑选产品，可对全部产品执行入库、批次生成、登记与查询；管理员自动拥有全系统权限。
5. **维护基础资料**：在“供应商”先建供应商与到货批次（入库数量、生产日期、到货日期、可用库存、安全库存），再在“产品管理”新建产品，为每行部件选择供应商、供应批次和每套用量。若产品是完整、不可拆分的成品，可不添加任何部件。
6. **可选对接领星**：在“系统设置”填写 AppID / AppSecret，并按企业实际开通的写入接口填采购/入库/库存同步地址；未配置时相关一键推送按钮会置灰。
7. **正式服务器部署**：改用 `settings.bat`（Windows）或 `settings.env`（Linux）设置强初始密码、随机 `PTS_SECRET_KEY` 和 `PTS_ENV=production`，详见下文《Windows 服务器部署配置》和《Linux 服务器部署》。

> 交付时数据库为空库：只包含这一个引导管理员账号和一个基线走步机型号（TW-04），没有任何示例产品、供应商、批次或历史记录，也不预置任何演示账号。

### 二、管理员日常（ADMIN）

- **数据概览**：今日完成/生成、待检、暂扣、库存预警、待处理质量记录与最近操作看板。
- **基础资料**：维护“产品管理”“供应商”“用户管理”与权限。
- **批次管理**：批次生成、现场批次登记、扫码查询、批次质量处理。
- **历史记录**：产品查询（族谱）与录入记录校对。
- **采购与生产**：采购订单、供应收货、生产订单、扫码枪入库、库存同步。
- **系统设置**：质量门禁开关、领星凭据与写入接口。

### 三、仓管日常（WAREHOUSE）

1. **批次生成**：选择任一产品（仓管可操作全部产品），填写前缀与计划台数，生成唯一批次二维码。
2. **现场批次登记**：扫码批次二维码；扫码枪回车自动提交，成功或失败后焦点都会回到扫码框。
3. **供应收货**：登记采购到货。
4. **生产订单**：选择采购订单生成唯一生产二维码。
5. **扫码枪入库**：扫描生产二维码后焦点自动跳到数量框，确认入库后回到二维码框，可连续作业；页面下方实时显示最近 50 条成品入库记录（产品、生产二维码、采购单、入库数量、入库后库存、操作人与时间）。
6. **扫码查询 / 历史录入记录**：核对任意产品的批次流向与历史逐台记录。

### 四、运营日常（OPERATIONS）

1. **我的产品**：登记并管理本人负责的采购产品（仅本人可见；管理员可见全部产品及添加人）。
2. **采购订单**：新建、编辑、复制采购单，一键推送领星或批量导出 48 列 Excel。
3. **扫码查询**：查询批次与产品去向。
4. **库存同步**：把当前成品库存单向同步到领星，并查看同步状态与审计。

## 当前业务结构

系统最终收敛为三个互斥角色：`ADMIN`（管理员）、`WAREHOUSE`（仓管）和 `OPERATIONS`（运营）。管理员维护基础资料、账号权限、质量状态与系统设置；仓管负责批次生成、批次登记、供应收货、生产订单与扫码枪入库；运营负责采购订单、领星推送、采购单导出、库存同步与工厂进度。走步机采用整批二维码溯源，历史逐台数据继续只读保留；非走步机的历史逐台流程仍兼容。

### 管理员流程

1. 在“供应商”添加供应商，进入供应商详情维护其部件、规格和到货批次。每个批次记录入库数量、生产日期、到货日期和可用库存。
   部件可设置安全库存；供应商详情可查看产品用料关联，以及每个批次的入库、领用和调整流水。
2. 在“产品管理”点击“添加新产品”，为每行部件依次选择供应商、部件、供应批次和每套用量；若产品是完整、不可拆分的成品（如供应商直供成品），可删除所有部件行，不配置任何部件。
3. 产品表单下方的“产品资料”维护产品档案字段（SPU、款名、型号、分类、报关与物流等）。其中“主图”是图片上传：选择 PNG / JPG / GIF / WEBP（不超过 5 MB）后立即上传并预览，保存产品后在产品卡片与详情页显示。SKU、品名、创建人、创建/更新时间和状态由系统自动填写。
4. 点击产品卡片进入详情页，可编辑产品、查看产品资料、部件库存和历史二维码生成批次。
5. 走步机使用“批次生成”，自定义前缀和计划台数（`1..999999`），每批只生成一个全局唯一码；系统先校验供应批次库存，再在同一事务中完成扣减、消耗关联与批次建档。非走步机的兼容逐台二维码流程仍支持单次最多 1000 套。
6. 点击生成批次可分页查看该批次二维码；可下载单套、单批全部或该产品历史全部二维码。
7. 在“用户管理”创建管理员、仓管或运营账号；仓管无需挑选产品，可操作全部产品的入库与批次作业，管理员自动拥有全系统权限。
8. 在“产品查询”先选择产品，再按二维码生成批次、完成日期、质量状态或关键词组合筛选；记录按日期分组，可通过主码、部件码查询产品族谱。
9. 新完成记录进入“待检”；管理员可逐条或批量确认“合格”、填写原因后“暂扣”，也可批量退回待检。录入员校对暂扣记录后，状态自动回到待检。
10. 产品族谱同时显示产品主码二维码和每个已绑定部件的二维码、编码、供应商与部件批次，方便现场直接复扫核验。
11. 管理员也可进入批次登记、生产订单、扫码枪入库和历史录入记录，执行排障或校对。

“数据概览”是管理员的生产运营工作台，集中显示今日完成、今日生成、待检、暂扣、库存预警、累计录入、待处理质量记录、库存异常和最近操作。

### 仓管流程

1. 在“批次生成”选择任一产品（仓管可操作全部产品），填写前缀与计划台数，生成唯一批次二维码。
2. 在“现场批次登记”扫描批次二维码；扫码枪附带的 Enter 会自动提交，成功或失败后焦点都会回到扫码框。
3. 在“供应收货”记录采购到货，在“生产订单”选择采购订单生成唯一生产二维码。
4. 在“扫码枪入库”扫描生产二维码，系统自动把焦点移到数量框；确认入库后清空表单并回到二维码输入框，可连续作业。本页下方的“成品入库记录”会立即显示刚完成的入库明细和入库后的成品库存。
5. 兼容逐台记录需要修改部件码时，先点击目标输入框再扫码，二维码只写入当前目标；回车后自动移到下一个部件输入框。

### 运营流程

1. 创建采购订单并推送领星，查看同步状态和审计记录。
2. 导出符合领星 48 列模板的采购单 Excel。
3. 查看关联生产订单和累计成品入库数量，并把当前成品库存单向同步到领星。

### 二维码规则

管理员自定义前缀，系统按当天日期和四位流水号递增：

```text
TABLE-A-20260718-0001
TABLE-A-20260718-0002
TABLE-A-20260718-0003
```

每个产品主码、每个部件码都具有数据库唯一约束。同一套的主码和部件码在生成时即完成绑定；扫码时会校验所选产品、二维码套件和部件顺序。扫描重复码会明确显示“扫描重复，请检查”。

## 多电脑和多扫描枪

- 一台服务器电脑运行本系统，其他工位电脑使用浏览器访问服务器地址。
- 每个浏览器自动生成独立工位标识，扫码会话按“账号 + 工位”隔离。
- 同一进行中的工位不能被另一个账号接管；原账号清空流程后才允许交接。
- 成品和部件在扫码期间会被占用，其他工位不能重复使用。
- SQLite 使用 WAL、写事务和唯一约束，多工位同时操作不会生成重复 SN、重复部件归属或重复归档。
- 扫码会话 8 小时无活动后自动释放。

扫描枪应支持 USB 键盘模式、二维 QR，并设置扫码后自动发送 Enter。

### 扫码枪现场验收

1. 登录仓管账号，进入“现场批次登记”；扫码批次二维码后，主键盘 Enter 和小键盘 Enter 都应自动提交并回到扫码框。
2. 进入“扫码枪入库”，扫描生产二维码后焦点应自动进入“入库数量”；确认入库后焦点应回到生产二维码输入框。
3. 在兼容逐台记录的修改弹窗中，先点击任一部件输入框再扫码，二维码只能写入当前输入框；回车后焦点自动移到下一个部件。
4. 重复码、无效码或无权限产品必须显示明确错误，且不能创建半条登记或重复库存记录。

扫码枪需要处于 HID 键盘模式。如果设备被配置为串口模式、厂商专用驱动模式，或二维码本身无法被识别，浏览器无法直接接收字符，应先使用记事本验证扫描后能否出现完整编码和换行。

## 本地安装和启动

要求 Windows 和 Python 3.11 或更高版本。

1. 双击 `install.bat`。脚本会在本目录创建 `.venv`，不会污染其他项目。
2. 双击 `start.bat`。若环境不存在或缺少依赖，启动脚本会自动修复。
3. 浏览器打开 `http://127.0.0.1:5080`。
4. 使用默认管理员首次登录并立即修改密码。

局域网其他电脑访问 `http://<服务器电脑IP>:5080`。如果无法连接，请允许 Windows 防火墙 TCP 5080 入站，并确认工位与服务器处于同一局域网。

## Windows 服务器部署配置

1. 将 `settings.example.bat` 复制为 `settings.bat`。
2. 修改其中的管理员初始密码和 `PTS_SECRET_KEY`。可用以下命令生成随机密钥：

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))"
```

3. 保持 `PTS_ENV=production`。生产模式会拒绝使用短会话密钥或默认管理员密码启动。
4. 根据服务器设置修改 `TRACE_PORT`。`TRACE_HOST=0.0.0.0` 表示允许局域网访问。
5. 如果通过 HTTPS 反向代理访问，将 `PTS_HTTPS_ONLY=1`；纯内网 HTTP 暂时保持 `0`。
6. 双击 `start.bat` 启动 Waitress 服务。

`settings.bat` 已加入忽略列表，不应提交、复制到公共位置或发给普通工位。服务端只运行一个 Waitress 进程和一份数据库；不要在多台电脑分别复制数据库后各自启动，否则数据无法实时合并。


### 领星 OpenAPI 配置

- 当前领星开放平台使用 `AppID` 和 `AppSecret` 两个凭据；系统不再要求虚构的 `id` 字段。
- Token 和 Refresh Token 默认调用 `https://openapi.lingxing.com` 的官方认证路径，业务请求按领星规则生成 MD5 + AES-ECB 签名。
- 领星要求将服务器公网出口 IP 加入开放接口白名单；未加白时 Token 接口会拒绝访问。
- `PTS_LINGXING_INBOUND_URL` 和 `PTS_LINGXING_INVENTORY_URL` 只能填领星为当前企业开通并在接口文档中明确的写入路径。未配置时系统会在外部请求前安全中止，不会把本地单据误标为已同步。
- 三个推送按各自接口是否配置分别启用：采购下单接口配好后，“推送领星”即可使用，不需要等入库、库存接口。

#### 采购单下单（推送领星）

- 接口：`POST /erp/sc/routing/purchase/purchase/setOrders`，已作为“采购订单接口”的默认值内置，通常无需填写。
- 语义：把领星中**已存在**的采购单从“待下单”改为“待到货”。它不创建采购单，因此需要先把采购单导入领星（用本系统的采购单 Excel 导出即可）。
- 请求：`{"order_sn": ["PO210705007"]}`。系统按“显式传入的单号 → 已记录的领星单号 → 模板中的采购单号 → 本地采购单号”依次取值；本地单号正是导出 Excel 写入领星的那个号。
- 成功返回 `code: 0` 且 `data` 为空数组（不返回对象 ID），系统据此把该采购单标记为已推送，并记录提交的采购单号。
- 失败返回 `code: 1`，真正的原因在 `data[].detail`（如“错误：采购单状态已变更”），而 `message` 仍是 `success`。系统会把每单的 `detail` 原文回显到界面并写入 `push_error`；`code: 0` 但 `data` 中含拒绝明细时同样视为失败，不会误标为已同步。

当前 SQLite + Waitress 适合单工厂中小规模并发录入。如果未来跨厂区、高并发或需要高可用，应把数据库迁移到 PostgreSQL/MySQL，并在 HTTPS 反向代理后部署应用服务。

## Linux 服务器部署

项目已提供 Linux 启动脚本、systemd 服务和 Nginx 配置示例：

- `install-linux.sh`
- `start-linux.sh`
- `settings.example.env`
- `deploy/systemd/product-traceability.service`
- `deploy/nginx/product-traceability.conf`

以下示例使用 `/opt/product-traceability`：

```bash
sudo useradd --system --home /opt/product-traceability --shell /usr/sbin/nologin traceability
sudo mkdir -p /opt/product-traceability
sudo cp -a . /opt/product-traceability/
sudo chown -R traceability:traceability /opt/product-traceability
cd /opt/product-traceability
sudo -u traceability chmod +x install-linux.sh start-linux.sh
sudo -u traceability ./install-linux.sh
```

生成生产密钥并编辑配置：

```bash
openssl rand -hex 32
sudo -u traceability nano /opt/product-traceability/settings.env
```

至少修改以下内容：

```dotenv
PTS_ENV=production
PTS_SECRET_KEY=替换为至少32位随机密钥
PTS_BOOTSTRAP_ADMIN_PASSWORD=替换为强初始密码
TRACE_HOST=127.0.0.1
TRACE_PORT=5080
```

先手动验证：

```bash
sudo -u traceability ./start-linux.sh
curl http://127.0.0.1:5080/api/health
```

验证成功后配置 systemd：

```bash
sudo cp deploy/systemd/product-traceability.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now product-traceability
sudo systemctl status product-traceability
```

查看服务日志：

```bash
sudo journalctl -u product-traceability -f
```

修改 `deploy/nginx/product-traceability.conf` 中的域名后启用 Nginx：

```bash
sudo cp deploy/nginx/product-traceability.conf /etc/nginx/conf.d/product-traceability.conf
sudo nginx -t
sudo systemctl reload nginx
```

公网部署必须配置 HTTPS；HTTPS 生效后把 `settings.env` 中的 `PTS_HTTPS_ONLY` 改为 `1`，再运行 `sudo systemctl restart product-traceability`。`settings.env` 已加入忽略列表，不应提交到仓库。

## 数据、升级和备份

- 主数据库：`data/traceability.db`
- 备份目录：`exports/backups`
- Excel：由浏览器下载到用户选择的位置

### 维护命令

```bash
python manage.py backup                  # 备份 + 自检 + 生成校验清单
python manage.py verify-backup FILE      # 校验备份是否可用
python manage.py restore FILE --yes      # 用备份覆盖当前数据库
python manage.py integrity-check         # 检查当前数据库
python manage.py audit-verify            # 校验审计账本哈希链
python manage.py audit-info              # 审计账本规模与事件分布
python manage.py login-status            # 登录失败计数与锁定状态
python manage.py login-unlock --username X  # 解除某账号的登录锁定
python manage.py db-info                 # 结构版本与各表记录数
python manage.py list-backups
python manage.py prune-backups --keep 30
python manage.py preflight               # 升级前检查（含自动备份）
python manage.py postflight              # 升级后检查
```

Windows 下双击 `backup.bat` 等价于 `python manage.py backup`。

备份使用 SQLite **在线备份 API**，服务运行时也能得到一致副本，并在生成后立即执行
`PRAGMA integrity_check`，同时写入 SHA-256 校验清单（`.manifest.json`）。
`restore` 会先核对校验和，并在覆盖前自动保留一份**恢复前副本**。

> **备份但不能恢复，等于没有备份。**
> 请按 [`docs/BACKUP_RESTORE.md`](docs/BACKUP_RESTORE.md) 的**恢复演练**章节
> 每季度实际执行一次。
> 另请注意：**同一块盘上的备份不能抵御磁盘损坏**，务必复制到另一块磁盘或受控文件服务器。

## 数据唯一性和审计

- 产品主码由“管理员前缀 + 当天日期 + 四位流水号”组成，同一前缀当天从 `0001` 递增。
- 产品主码、产品识别码、部件码、二维码套件号、溯源单号和审计事件号均有数据库唯一约束。
- 每个部件码在生成时绑定到一个产品主码和一个固定部件顺序，不能混用另一套产品的部件码。
- 非空供应商单件序列号全局唯一。
- 一个成品只能有一条最终归档，一个部件标签只能归属一个成品。
- 已生成二维码的产品锁定当时的部件清单，不受后续配置影响。
- 产品定义绑定供应批次；实际生成产品码时才按“套数 × 每套用量”扣减可用库存。库存不足时整次事务回滚，不产生半批二维码或错账。
- 供应批次调整不能把入库数量改到已领用数量以下；收货、领用和调整均保留库存流水。
- 部件结存为 0 时进入缺货预警；结存大于 0 且不高于管理员设置的安全库存时进入低库存预警。
- 录入记录按“待检、合格、暂扣”管理；暂扣必须填写原因，记录校对后自动重新进入待检。
- 登录账号是生成、录入、扫码和归档操作的真实审计身份，前端不能伪造操作员名称。
- 产品创建、成套二维码生成、开始录入、部件扫码、录入完成、记录修改和记录删除均写入审计事件。

角色权限的**唯一权威来源**是 `traceability/capabilities.py` 的能力表：

- `Capability` 枚举定义「能做什么」，`ROLE_CAPABILITIES` 定义「哪个角色能做什么」。
- 路由用 `require_capability(Capability.X)` 判权，不再散落角色判断。
- 该模块**不依赖 Flask**，因此文档工具与测试都能导入它，权限矩阵无法再与代码脱节。
- `ADMIN` 持有全部能力（超集）；`require_warehouse()` 与 `require_admin_or_warehouse()`
  现为同一实现。

**现场写操作是幂等的。** 扫码枪或抖动局域网把同一次提交投递两次时，
服务端重放已存响应而不是重复执行——否则**成品库存会被重复累加**。
客户端通过 `Idempotency-Key` 请求头（或 body 的 `idempotencyKey`）携带幂等键，
键在业务逻辑**之前**占位，**占位本身就是互斥锁**。详见
[`docs/API_CONTRACT.md`](docs/API_CONTRACT.md) §6。

## 后续演进顺序

结合当前数据基础，后续建议按闭环优先级推进，而不是先增加大量只有展示效果的页面：

1. 生产工单和 BOM 快照：把成品建档、计划数量、班次、线体和装配进度统一到工单。
2. 完整 QMS：在当前待检/合格/暂扣状态上增加质检员角色、检验任务、抽样方案、检验项目和测量值。
3. 不合格品与返工闭环：隔离、评审、处置、返工工单、复检，以及归档族谱的受控更正。
4. 打印与补打控制：模板版本、打印次数、作废/补打原因和审批审计。
5. 召回、库位与 ERP/MES 接口：在现有批次库存流水上扩展仓库、库位、领退料单和外部单据号，避免后续重复迁移。

## 使用边界

不要把未配置 HTTPS 和访问控制的 5080 端口直接暴露到互联网。当前版本聚焦产品二维码、部件绑定、人员授权、现场扫码和族谱追溯，尚未替代完整的检验任务、审核放行、不合格品、返工、工单排产、仓储收发、ERP/MES 对接或跨数据库高可用方案。
