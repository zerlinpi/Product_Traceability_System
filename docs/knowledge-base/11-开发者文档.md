## 开发环境

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt -r requirements-dev.txt
cd frontend && pnpm install
```

### 启动

```bash
python tools/dev_server.py --port 5090    # 后端（开发，带种子数据）
cd frontend && pnpm dev                   # 前端（热更新）
```

## 测试

```bash
.venv/Scripts/python -m pytest tests -q           # 全部后端测试
.venv/Scripts/python -m pytest tests/test_batch_query.py -q   # 单个文件
cd frontend && pnpm typecheck && pnpm build       # 前端检查与构建
cd frontend && pnpm e2e                           # E2E（需先起服务）
.venv/Scripts/python tools/acceptance.py          # 端到端业务验收（场景 A–J）
.venv/Scripts/python tools/smoke.py               # 真实 HTTP 冒烟（起服务→打→关）
```

> `tools/smoke.py` 与其余测试的区别：其余测试走 Flask 的 test client，**从不打开 socket**。
> 凡是只有真实连接才成立的东西——浏览器实际发出的 cookie、部署实际设置的响应头、
> gzip 协商、`Cache-Control`、从外部看到的 CSRF 要求——只有它覆盖。
> 登出失效那个 bug 就是它发现的：`session.clear()` 在单元测试里看起来完全正确
> （被调用那个客户端确实登出了），而 cookie 的副本一直能用，
> 因为整套测试里从没有人持有过第二份 cookie。

## 门禁（提交前必须全过）

```bash
python -m ruff check .                        # 静态检查
python tools/check_docs_consistency.py        # 文档与代码一致
python tools/check_knowledge_base.py          # 知识库链接完整、无孤立页面
python tools/extract_routes.py --check        # 权限矩阵同步
python tools/check_frontend_build.py          # 构建产物与源码一致
python tools/check_test_count.py              # 测试数量不低于基线
python -m pytest tests -q --cov=app --cov=traceability --cov=manage --cov=tools --cov-fail-under=82
```

> **coverage 为什么没有 tools/acceptance.py、dev_server.py、build_frontend.py**：
> 这三个是构建与验收工具，本身由 CI 的 Acceptance / Frontend 作业直接执行，
> 不属于「发到现场的那套系统」。把它们计进分母会让覆盖率因为与运行时无关的原因
> 波动（见 `pyproject.toml` 的 `[tool.coverage.run]`）。门槛仍是 82，没有下调。

## 前端构建（**重要**）

**必须**用官方工具，不要直接用 `pnpm build`：

```bash
python tools/build_frontend.py
git add static/dist
git commit -m "build: refresh the committed front-end bundle"
```

原因：只有它会生成

- `static/dist/build-info.json`（源码指纹，门禁据此判断产物是否过期）
- 各资源的 `.gz` 兄弟文件（服务端在客户端支持 gzip 时直接发送，省约 30% 流量）

## 代码约定

| 项 | 约定 |
| --- | --- |
| 列表接口 | 必须**有界**，用 `traceability/pagination.py` |
| 对象级权限 | 路由里调用 `require_product_model_access` / `require_supplier_access` |
| 写操作 | 加 `Idempotency-Key` 支持，防止重复提交 |
| 错误信息 | 面向用户的中文，明确指出字段 |
| 数据库变更 | 升结构版本 + 迁移 + 迁移矩阵测试 |
| 注释 | 解释**为什么**，不是解释代码在做什么 |

## 数据库迁移

- 结构版本在 `traceability/db.py`。
- 迁移必须**可重复执行**且**向前兼容**。
- 改结构要同步更新 `docs/DATA_MODEL.md` 与迁移测试。

## 关键设计说明

### 列表窗口

列表接口返回**普通数组**（不改变响应体形状），窗口信息走响应头：

| 响应头 | 含义 |
| --- | --- |
| `X-Total-Count` | 筛选后总行数 |
| `X-Returned-Count` | 本次返回行数 |
| `X-List-Limit` | 生效的窗口大小 |

前端 `PtsListWindowNotice` 读取这些头，在超窗口时提示用户。
**导出不受窗口限制**——文件不是屏幕。

### 领星超时语义

`LingxingError.uncertain` 表示**结果未知**（请求已发出、无回复）：

- **写操作不自动重试**（可能已写入，重试会产生重复单据）
- 铸造 token 幂等，仍可重试
- 记录为 `PO_PUSH_UNKNOWN` 审计事件，并提示操作员**先核对再重试**

> 判断「能否重试」取决于操作**是否幂等**，不是网络错误本身。
> 把重试策略写在传输层必然出错——那里看不到操作语义。
