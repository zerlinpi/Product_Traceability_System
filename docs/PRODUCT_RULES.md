# 业务规则（真实基线）

> 基线：以**现有生产行为 + 测试**为准。凡文档与代码冲突，以代码为准并在此记录冲突。
> 数据模型见 `DATA_MODEL.md`，权限见 `PERMISSION_MATRIX.md`，接口见 `API_CONTRACT.md`。

---

## 1. 产品定位与部署边界

单工厂、**局域网优先**部署的轻量 MES/WMS/QMS 溯源系统。

- 一台服务器电脑运行服务，其他工位用浏览器访问同一地址。
- 默认数据库 SQLite（WAL 模式），应用服务器 Waitress。
- **明确不做**：微服务、Kubernetes、消息中间件、分布式部署。
- 演进方向是 **Modular Monolith**，为 PostgreSQL/MySQL 适配预留结构，但**当前不改默认数据库**。

## 2. 角色

恰好三个互斥角色，账号持**单值** `role`，不能同时兼任：

| 角色 | 定位 |
| --- | --- |
| `ADMIN` | 管理员，全系统权限 |
| `WAREHOUSE` | 仓管，现场作业 |
| `OPERATIONS` | 运营，采购与领星对接 |

历史 `OPERATOR` 在 v14 迁移映射为 `WAREHOUSE`。数据库 CHECK 约束会**拒绝**新的 `OPERATOR`。

### ⚠️ 冲突 C1：仓管可见的产品范围

| 来源 | 描述 |
| --- | --- |
| `SYSTEM_ARCHITECTURE.md`（**已过时，已修正**） | 仓管「只看到管理员分配且启用的产品」 |
| `auth.py` `current_operator_id()` 注释 | 仓管处理**每一个**产品，范围检查按不受限处理，**与管理员一致** |
| `README.md` | 仓管「可对**全部产品**执行入库、批次生成、登记与查询」 |

**基线判定：仓管可操作全部产品。** 已修正 `SYSTEM_ARCHITECTURE.md`。

副作用：`require_product_model_access()` 与 `require_supplier_access()` 是**空操作**，
范围授权表仍写入但**不再拦任何请求**。此前有 12 个路由只依赖这两个空操作守卫，
**已于本批次补挂显式能力守卫**（见 `PERMISSION_MATRIX.md` D2）。

### ⚠️ 冲突 C2：运营的产品可见性

- 运营只能看到**本人创建**的产品与采购订单（`created_by_user_id` 过滤，`app.py:7074` 等）。
- 管理员可见全部产品及添加人。
- 这是**数据范围过滤**，不是鉴权拒绝——即运营请求他人产品时得到的是空列表/404，而非 403。

## 3. 核心数据链

```
供应商 → 供应部件 → 供应库存批次 → 产品用料（每套用量）
                                  ├→ 生产批次（唯一批次码）
                                  │    └→ 批次登记 → 质量状态 → 正/反向追溯
                                  └→ 历史逐台二维码套件（兼容只读/非走步机）

采购订单 → 供应收货 → 领星入库推送
    └→ 生产订单（唯一生产二维码）→ 扫码枪入库 → 成品库存 → 领星库存同步
```

---

## 4. 二维码规则

### 批次码（走步机，当前主线）

管理员自定义前缀，系统按当天日期 + 四位流水号递增：

```text
TABLE-A-20260718-0001
TABLE-A-20260718-0002
```

- 计划台数范围 `1..999999`，**每批只生成一个全局唯一码**（整批溯源）。
- 生成前先校验供应批次库存，再在**同一事务**内完成扣减、消耗关联与批次建档。
- 批次码全局唯一。

### 历史逐台套件（非走步机兼容）

- 一套 = 一个产品主码 + N 个部件码，生成时即完成绑定。
- 单次最多 1000 套。
- 扫码时校验所选产品、套件与**部件顺序**。
- 扫描重复码显示「扫描重复，请检查」。
- **只读保留**，走步机产品的新逐台入口已退役（直接调用返回 409）。

### 前缀与流水

产品主码由「管理员前缀 + 当天日期 + 四位流水号」组成，同一前缀当天从 `0001` 递增。
产品主码、产品识别码、部件码、二维码套件号、溯源单号、审计事件号**均有数据库唯一约束**。

## 5. 库存规则

- **事实来源是流水**：`supplier_inventory_movements` 记录每次入库/领用/调整的
  `quantity_delta` 与**变动后结存**。
- 扣减时机：**产品码生成时**，按「套数 × 每套用量」计算；**不是**在产品定义时。
- 库存不足 → **整次事务回滚**，不产生半批二维码或错账。
- 供应批次调整**不能把入库数量改到已领用数量以下**。
- 成品库存由 `inbound_scan_records` 累加，两者**同事务**写入。
- 预警：结存为 0 → 缺货预警；结存 > 0 且 ≤ 安全库存 → 低库存预警。

## 6. 质量闭环

```
ASSEMBLED --pass--> PASSED     （需 ADMIN）
ASSEMBLED --hold--> HOLD       （需 ADMIN，原因 1-500 字符）
其他状态 --任意--> 409 拒绝，状态不变
```

- 新完成记录进入 `ASSEMBLED`（待检）。
- 暂扣**必须填写原因**。
- 录入员校对暂扣记录后，状态自动回到待检。
- 质量状态变更写入审计事件，含操作者、前/后状态、时间、原因。
- 管理员可逐条或批量确认，也可批量退回待检。

> **注意**：`/pass` 与 `/hold` 是同一状态机的两个方向，但 `require_admin()` 一个写在
> **service 层**、一个写在 **handler 层**（详见 `PERMISSION_MATRIX.md` D5）。

## 7. 多工位与扫码枪

- 每个浏览器自动生成独立**工位标识**，扫码会话按「账号 + 工位」隔离。
- 同一进行中的工位**不能被另一个账号接管**；原账号清空流程后才允许交接。
- 成品与部件在扫码期间被**占用**，其他工位不能重复使用。
- 扫码会话 **8 小时**无活动后自动释放。
- SQLite 使用 WAL + 写事务 + 唯一约束，多工位并发不会产生重复 SN 或重复归档。

### 扫码枪要求

- 必须为 **HID 键盘模式**、支持二维 QR、扫码后自动发送 Enter。
- 主键盘 Enter 与小键盘 Enter **都应**触发提交。
- 扫码枪入库：扫生产二维码 → 焦点自动移到数量框 → 确认后回到二维码框，可连续作业。
- 串口模式或厂商专用驱动模式**无法**被浏览器接收，应先用记事本验证。

## 8. 采购与领星

- 采购单导出为**领星 48 列模板** Excel。
- 领星凭据为 `AppID` + `AppSecret`；签名 MD5 + AES-ECB。
- 领星要求把服务器**公网出口 IP 加入白名单**，未加白时 Token 接口拒绝访问。
- 「推送领星」把领星中**已存在**的采购单从「待下单」改为「待到货」——**它不创建采购单**，
  需先用本系统导出的 Excel 把采购单导入领星。
- 三个推送按各自接口是否配置**分别启用**：采购下单接口配好即可用，无需等入库、库存接口。
- 写接口未配置时系统在**外部请求前安全中止**，不会把本地单据误标为已同步。

## 9. 审计规则

以下操作**均写入审计事件**：

产品创建、成套二维码生成、开始录入、部件扫码、录入完成、记录修改、记录删除、
批次质量状态变更、用户创建/更新/登录/登出/改密、领星推送与同步。

- 登录账号是**真实审计身份**，前端**不能伪造**操作员名称。
- 事件号唯一，记录操作者与时间。

> **缺口（属第十七目标）**：`audit_events` 目前是**普通表**，
> 应用层未禁止 `UPDATE` / `DELETE`，无数据库级触发器，无 hash chain。
> 作为产品追溯证据，它还不是 append-only ledger。

## 10. 记录修改与删除

- 可编辑状态：见 `record_status_payload()`（`app.py`）。
- 删除**必须填写原因**（1-200 字符），写入 `TRACE_RECORD_DELETED` 审计事件。
- 允许的角色：**ADMIN + WAREHOUSE**（`Capability.RECORD_EDIT` / `RECORD_DELETE`）。
  运营**无权**——依据前端 `allowedViews()` 中 `my-records` 不在运营视图列表。

> **✅ 越权面已关闭（原 D3）**：此前这三个路由只挂空操作范围守卫，
> 任何已登录账号（含运营）都能改删任意录入记录。现已补挂显式能力守卫。

> **⚠️ 仍未实现：归属权规则。** `editable_record()` 中存在
> 「只能修改或删除自己的录入记录」的检查，但它是**死代码**
> （`current_operator_id()` 恒返回 `None`），错误消息不可达。
> 即：**仓管之间可以互相校对记录**，没有「只能改自己录入的」这条规则。
>
> **待业务确认**：这是否符合预期？若要求「只能改自己的」，
> 需让 `current_operator_id()` 恢复返回真实 user id，
> 并同步调整 `require_product_model_access()` 的语义——属于**业务决策**，
> 本批次不做假设。

## 11. 数据、升级与备份

- 主数据库：`data/traceability.db`
- 在线备份：`backup.bat`（使用 SQLite 在线备份 API，服务运行中也能得到一致副本）
- 备份目录：`exports/backups`
- Excel 由浏览器下载到用户选择的位置

升级步骤：

1. 先执行 `backup.bat` 并确认生成备份文件
2. 停止服务窗口
3. 替换程序文件，**保留** `data/traceability.db` 和私有 `settings.bat`
4. 运行 `install.bat` 更新依赖，再运行 `start.bat`

启动时只执行**增量**建表/加列和旧数据映射，**不删除**已有成品、部件、账号或溯源记录。

> **缺口（属第十八/三十九目标）**：`manage.py` 目前仅 38 行，只有备份入口；
> 缺少 `verify-backup` / `restore` / `integrity-check` / `db-info` / `preflight` 等命令。
> **备份但无法验证恢复，等于没有备份。**

## 12. 生产环境守卫

`PTS_ENV=production` 时，`app.py:1659-1669` 会在启动时**直接抛 `RuntimeError` 拒绝启动**：

- `SECRET_KEY` 为默认值或示例值，**或**长度 < 32
- `BOOTSTRAP_ADMIN_PASSWORD` 为默认值或示例值

本地开发默认管理员：`admin` / `Admin@12345`，**首次登录强制改密**。
该默认值出现在 `README.md`、`app.py:84` 与测试中，属**有意公开的本地开发默认值**，
生产守卫使其无法用于生产部署。
